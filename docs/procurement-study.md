# 購買業務の評価：最初の19操作

25操作の評価アプリのうち、申請作成・変更・申請・取り下げ・承認・却下・差し戻し・担当変更・発注・発注変更・発注取消・発注完了・検収・請求登録・請求照合・請求承認・請求無効化・支払記録・支払取消を実装した。
これは講演の実製品を再現した仕様ではなく、Koyukiの開発体験を検証するための独自の評価仕様である。
残り6操作と通常TypeScript／helper版との同条件比較は未実施。

## 実装と境界

- `src/experiments/procurement/domain.ts`：状態Union、検証済み明細、検証・純粋な状態遷移。
- `src/experiments/procurement/application.ts`：既存business APIによる5モデル・19操作の登録。新しいcore APIは追加していない。
- `src/experiments/procurement/repository.ts`：同期／非同期の読込みを許すportと、メモリadapter。
- `src/procurement.test.ts`：一連の成功・業務失敗・競合・複合保存の検証。

業務の流れは、draft → submitted → approved の申請から発注を作り、分納の検収記録と請求を照合する。
状態判別子を書き換えるだけでは承認済みの非公開brandを作れない。共通saveの戻り値はRequest Unionなので、
承認操作の公開結果もUnionのままになる。この契約を型検査で固定し、Approvedだけを返すとは主張しない。

## この段階で固定した仕様

金額は単一通貨の整数最小単位とし、税・為替を扱わない。明細は1〜1000件、SKUは重複不可、数量・単価は正の安全な整数、合計も安全な整数とする。
申請上限は1申請当たりの上限であり、共有予算の残高管理ではない。
申請者はbuyer、承認者は指定されたapprover、検収者はwarehouse、請求担当はfinance。
認証済みactorはhostが注入し、入力から所有者やgroupを上書きできない。認証基盤そのものは提供しない。

1申請に有効な発注は1件、1発注に有効な請求は1件とする。取消発注は残し、同じ承認済み申請から別IDの発注を作れる。完了発注は再発行できない。無効化済み請求は残し、別IDで再登録できる。
分納を許し、SKUごとの累計検収数が発注数を超えない。請求登録は未入荷・金額不一致でも可能だが、
照合は全数検収済みかつ発注額との一致を要求する。不一致請求は無効化して別IDで登録し直す。
業務IDは実行要求IDではなく、このサンプルには永続receiptによる再送制御をまだ付けていない。

検収では発注version更新と検収記録追加を同じChangeに含める。
adapterは全version・一意制約・書込みの対応を確認し、全値のcloneを済ませてから同期的にMapを更新する。
古いversionや途中のclone例外ではどちらも保存しない。これは単一プロセス内のメモリ実装の性質であり、DB transactionや別プロセス間の保証ではない。
業務全体を一つのtransactionにせず、後段で失敗しても先行する申請や発注は残る。

## 接続を任せられたことと、残った弱点

businessが宣言したload → run → saveの実行とResultの失敗伝播、詳細traceを共通化する。
利用者は各純粋関数内で業務判断を記述する。非同期repositoryも同じ宣言で使える。

一方、複数モデルを読むloadでは依然としてResultの分岐とjoinを書いている。
フレームワークは必要な照会や整合性境界を推測しない。全データ取得を隠したという結果ではない。
共通saveの広い戻り値により、操作ごとの到達状態が公開結果から失われる点も残る。

検収結果はReceiptだけを返すが、保存時にはOrderのversionも変わる。
Applicationを接続する際には、両方を返す結果型か再取得が必要になる。
ReceiptだけでOrderの画面状態まで自動更新できるとは扱わない。
これは複数モデルをつないで初めて明確になった出力・投影の設計課題である。

## 申請の修正・承認のやり直し

| 入力状態 | 操作と実行者 | 成功状態 | 主な拒否条件 |
| --- | --- | --- | --- |
| draft | 変更：所有者buyer | draft、明細と合計を再検証 | 空明細・不正金額・非所有者 |
| submitted | 取り下げ：所有者buyer | draft | 承認後・非所有者 |
| submitted | 差し戻し：現在の担当approver | draft | 非担当者 |
| submitted | 担当変更：現在の担当approver | submitted | 所有者・未登録者・同一担当への変更 |
| submitted | 却下：現在の担当approver | rejected | 空理由・1000文字超・非担当者 |

全操作でgroup・有効なactor・期待versionを確認する。却下は終端とし、再利用せず新規申請を作る。
差し戻しと取り下げではdraftを明示的に再構築し、旧approverIdなどの不要フィールドを残さない。
差し戻し理由の保存・承認履歴の永続化はこの段階では提供しない。
承認と取り下げが競合しても同じsubmitted versionから保存できる遷移は一つだけである。

業務のやり直しは新しいruntime APIを必要とせず、同じloadとsaveへの操作登録で表せた。
ただし認可・version検証の重複はdomainに残るため、この評価domain内の小さな関数へ共通化した。
業務判断そのものをframeworkへ移したという意味ではない。

## 発注の変更・取消・完了

| 入力状態 | 操作 | 成功状態・条件 |
| --- | --- | --- |
| placed | 変更 | placed。所有者buyerが仕入先だけ変更し、承認済み明細・価格は保持。入荷・請求があると拒否 |
| placed | 取消 | cancelled。所有者buyerのみ。入荷・請求があると拒否 |
| placed | 完了 | completed。所有者buyerのみ。全数入荷と金額一致の照合済み／承認済み請求1件が必要 |

cancelled/completedはこの段階では終端。検収と請求登録はplacedだけを受け付ける。
請求登録は請求挿入と発注version更新を一つのChangeに含めるよう変更した。
入荷や請求の有無という「行がない」条件をloadだけで確かめても、競合する追加を防げないためである。
取消・変更・検収・請求登録が同じ発注versionを確認し、同時の保存は一つだけ成功する。
完了時は参照した請求versionも検査する。将来の返品・請求無効化にも、この境界を引き継ぐ必要がある。

取消した発注からの再発行はloadの判定だけでなく保存時の有効発注一意性でも制御する。
取消を含む過去行を消さず、同時に二つの再発行が有効になることを拒否する。
変更は仕入先のみであり、価格や数量を承認なしで変更できるという仕様にはしていない。

## 請求承認・無効化

financeだけがmatched → approvedへ遷移できる。approvedは承認者と照合した検収IDを保持し、
発注完了はmatchedまたはapprovedの請求を受け付ける。支払記録はapprovedの請求だけに作成できる。
registered/matchedの請求は、発注がplacedである間だけ理由付きでvoidedにできる。
approved/voidedからの無効化は拒否する。無効化は照合情報を持たない状態として明示的に再構築する。

無効化時は請求と発注versionを同時に更新し、発注完了と競合させる。
有効請求だけを一意制約と完了条件の対象にする。無効請求を除いた後は、入荷がなければ発注変更・取消も可能。

複数回のread/listはスナップショット読取りではない。無効化と完了の競合では、後者がConflictで止まる場合と、
新しい請求一覧を読みInvoiceMismatchで止まる場合がある。どちらも保存しない。
さらに無効化前に作った完了Changeを直接保存し、CASが古い計画を拒否することを検証した。
メモリadapterでの検証であり、任意のDB adapterがこの契約を満たす保証ではない。

## 支払記録と取消

financeはapprovedの請求に対してrecordedの支払記録を作れる。
金額は請求から導出し、入力に追加された金額は使用しない。支払IDと参照番号は前後に空白を持たない非空文字列、
参照番号は最大200文字とする。1請求にrecordedは1件まで、参照番号は同じgroup内で取消済みも含め再利用不可とする。
別groupのデータと制約を共有しない。記録時には請求versionと支払IDの未使用を確認する。

recorded → cancelledはfinanceが理由付きで実行する。取消は元の金額・参照番号・記録者を残し、取消者と理由を加える。
取消後は別支払ID・別参照番号で同じ請求へ記録し直せる。二重登録と二重取消は保存時にも検査する。
発注がcompletedでも請求のapprovedは保持され、支払記録の作成を妨げない。

ここで扱うのは実行済み支払の業務記録と、その記録の取消である。銀行への送金・返金・口座残高の変更は行わない。
請求のapprovedを支払時に別状態へ変えず、有効記録の一意性を保存境界で扱う。
取消済みの行を保持するが、これは変更ごとの永続監査ログではない。メモリを再起動すると消える。
