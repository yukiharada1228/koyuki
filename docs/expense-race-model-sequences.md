# 同じ版を読んだ並行要求を独立仕様と比較する

[競合モデル](../src/expenses/race-model-testing.ts)は、上長承認待ちの経費に対する二つの要求を、
独立したSQLite接続で実行する。金額100001・領収書あり・既定の定義versionを使い、
承認と却下の10ケースを対象にする。業務の期待値は既存の独立参照仕様から計算し、
receiptと版数の規則から、許される出力・最終状態・receipt数・変更履歴数の候補を先に作る。
実装の結果を見て期待値を作ったり、左側が常に勝つと仮定したりしない。

| 条件 | 保存境界での期待 |
| --- | --- |
| 同じID・同じ承認要求 | 一方がcommitted、他方がreplayed。業務状態の更新は一回 |
| 異なるID・同じ版の承認要求 | 一方がcommitted、他方がSaveConflict |
| 同じID・異なる理由や操作者（両方が検証成功） | 最初の成功要求を保存し、他方はIdempotencyConflict |
| 異なるID・異なる理由や操作者（両方が検証成功） | 保存順によって勝者・理由・承認者が変わり得る。もう一方はSaveConflict |
| 読み込み済み状態で自己承認・無効操作者・空理由を検証 | 該当の業務エラー。検証失敗では保存もreceipt追加も行わない |

両方が最初のreceipt照会を通り、同じ版2を読み終えるまで、どちらも次へ進めない。
その後は選んだ側を完了させ、もう一方が読み込み済みの状態で処理を続ける。
これにより、左右の完了順を制御しながら、両方のloadが保存前に完了した条件を検査する。
同期点にはテスト用の時間制限を設け、失敗時も両要求の終了を待ってから接続・ファイルを閉じる。

ここでは、二つのHTTP要求を最初から順番に実行するモデルでは足りない。
後から進んだ側も古い読み込み結果を検証するため、検証失敗と保存時の競合を分ける。
例えば自己承認は、他方が保存した後でも読み込み済み状態からSelfApprovalになり得る。
保存へ進んだ側についてだけ、同一要求の再取得・要求の衝突・CASを保存順に従って判定する。

## 確認した範囲

[検査](../src/expense-race-model.test.ts)は10ケースを左右両順、計20回実行する。
両接続が版2を読んだことをassertし、結果の組・全経費行・receipt数・変更履歴数を照合する。
件数には準備時の申請一回も含む。競合前はreceiptと変更履歴が各1件で、
競合で一方が成功すれば各2件、両方が拒否されれば各1件のままである。

別に3 seed・各12バッチ、計36バッチを生成する。一バッチの二要求は一つのテストイベントで、
バッチ間では同じDBを使い回さない。samplerの状態はバッチ番号であり、
36バッチを一つの長寿命の業務状態機械として探索したという意味ではない。
常に左側だけが勝つとする故意に誤ったoracleは、右側を先に進める一バッチで反例になる。
モデルと実装の不一致は、実装だけでなく期待仕様の誤りでも起こり得る。

同じ契約から雛形生成した3テストも、実tarballのconsumerで型検査・実行する。

```sh
node --import tsx --test src/expense-race-model.test.ts
npm run build
npm run --silent generate:model-test -- --contract ./src/expenses/race-model-testing.js > generated-expense-race-model.test.ts
node --import tsx --test generated-expense-race-model.test.ts
```

対象は同一プロセス内の独立接続と、制御した二つの進行順である。
全ての割込み点、別OSプロセスの同時書込み、別DB/driver、高負荷、配送喪失との複合故障を
この生成器で検証したとはしない。既存の別OSプロセスによる個別競合検査は維持する。
passed/sampledだけを任意の分散システムの正しさへ読み替えない。
