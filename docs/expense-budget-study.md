# 予算付き経費精算で何を任せられるか

既存の`src/expenses/domain.ts`を再利用した代表例。新しい業務実装は`src/experiments/expense-budget/`にある。AIによる実装・比較であり、人間の初見利用や本番性能の証拠とは区別する。

## 状態と予算の扱い

| 入力 | 操作 | 成功状態 | 予算の変化 |
| --- | --- | --- | --- |
| draft | 本人が申請 | manager、少額ならapproved | 金額を確保 |
| manager | 本人以外の上長が承認 | finance、高額でなければapproved | 確保を維持 |
| finance | 本人以外の経理が承認 | approved | 確保を維持 |
| manager / finance | 審査者が差し戻し | returned | 確保を解放 |
| returned | 本人が修正 | draft | 確保なし |
| 修正後draft | 本人が再申請 | manager / approved | 修正金額を確保 |

金額単位は整数の最小通貨単位。元の経費モデルの自動承認・経理承認閾値をそのまま使う。approvedはこの例では予算消費済みとして確保を維持し、支払・年度更新・複数通貨は扱わない。一つのDBに一部門という明示的な制約がある。

予算計算は`budgetChange`という純粋関数。業務上の予算超過はBudgetExceeded、古い取得値による保存競合はConflictとして区別する。後者を勝手に再計算・再実行しない。

## JSXと実行

`application.tsx`の`ExpenseBusiness`が申請・承認・差し戻し・編集をまとめて登録する。Repositoryはprops、Actorは上位Providerから供給する。`ExpenseNotifications`は保存後のイベント受信側を別部品として登録する。実行スコープごとにActorを捕捉し、リクエスト本文から操作者を採用しない。

型は操作ごとに入力を保つ。差し戻しにはreason、編集にはamountとreceiptが必要。汎用の操作生成関数一つへまとめる案では、未確定genericに対するNeedsInputの計算が解決しないことがあった。型アサーションで隠さず、四つの具体的ResourceとOperationを残した。共有の保存・再送境界は`boundary`にまとめている。これは現時点の記述上の負担である。

## 保存アダプターの契約

SQLiteはBEGIN IMMEDIATE内で次を行う。

1. requestIdの成功記録を再確認し、同内容ならreplayed、別内容ならIdempotencyConflict。
2. 経費のexpectedVersionと遷移の妥当性を検査。
3. 取得した予算のID・version・残額を現在値と照合し、純粋関数でdeltaを再検査。
4. 経費と予算を更新。
5. outbox・監査・成功記録を追加しCOMMIT。途中失敗ならすべてROLLBACK。

異なる経費でも予算を共有するので、経費のversionだけでは超過を防げない。今回は予算versionも比較する。予算deltaが0の承認でも保守的に予算の一致を要求するため、無関係の予算更新が承認を競合させる場合がある。最適化前の安全側の制約として明示する。

メモリ版も比較から更新までawaitせず、同じ契約を満たすが再起動では消える。`contracts.ts`の`checkRepositoryContract`は任意のassertionライブラリを渡して再利用できる検査で、SQLite・メモリの両方へ適用している。観測用snapshotはテスト用インターフェースであり、実運用Repositoryに一覧読み取りを強制するものではない。

requestIdはDB内で一意。同じkeyに別の操作・入力・操作者属性を対応させることは拒否する。保存された成功値は元の要求の結果であり、後から変更した現在状態に書き戻さない。復元は状態・ID・version・操作との対応を検査する。fingerprintは認証や改ざん防止署名の代用ではない。

監査はこの例ではtransaction内の記録なので失敗時に業務保存もrollbackする。任意の外部監査サービスへの送信完了まで保証するものではない。通知は保存後なので失敗しても業務成功を維持する。outboxの配送・ack・外部通知の重複排除はホスト責務である。

## 通常のTypeScriptとの比較

`plain.ts`は同じ純粋関数、入力検証、Repository、再送契約を使う。取得→計算→保存→想定内失敗時のreceipt再確認→成功後通知を明示的に書く。比較試験では申請・上長承認・予算超過・差し戻し・編集・再申請・再承認・経理承認・過去要求の再送を両方で実行し、結果・最終状態・予算・receipt・イベントpayload・監査件数の一致を検査する。イベントのUUIDは比較から除く。

この一例でKoyukiの総行数が少ないとは主張しない。Context・Resource・JSXの構成コードは導入コストである。一方、型付き操作参照、内部の実行通知、イベント受信側の独立したスコープ、構成時検査は共通の実行器を利用できる。plain版はこれら全部を再実装した完全同機能の競合実装ではない。この差を無視した行数・速度ランキングは作らない。

現在の比較で分かるのは、業務・保存の共通化が可能なことと、実行接続の負担をどこへ移せたか。単純な一操作ではplain版が十分。複数業務に同じ実行契約を維持したい場合、Koyukiの価値が出る。

未検証は本番負荷・実際のメール・人間の初回学習・他のDBの分離レベル。承認閾値の変更比較は下記の範囲で実施したが、開発生産性全般を証明したとはしない。


## 仕様変更の差分を比較した結果

配布物検証内で、利用者の作業ツリーへ触らず隔離consumerの閾値を100000から50000へ変更する。共有の`expenses/domain.ts`の5行（遷移と復元検証）、`examples/expense.ts`の1行（申請時の経路計算）が変わる。境界値の期待を独立に49999 / 50000 / 50001へ変更するテストは1行。両実装で変更後のシナリオを実行し、閾値ちょうどは上長承認で完了し、1単位超過すると経理承認待ちになることを確認する。

| 変更対象 | Koyuki | 通常TypeScript |
| --- | --- | --- |
| 共有の業務モデル | 2ファイル・6行 | 同じ共有実装 |
| 実行の接続 | 0行 | 0行 |
| 保存アダプター | 0行 | 0行 |
| 共有の境界値テスト | 1行 | 同じ共有試験 |

この結果は両方が関数型の核の分離から恩恵を受ける証拠であり、Koyukiの方が変更が少ないという結果ではない。状態復元にも閾値が含まれているため、変更が単一の定数編集には収まっていないことも記録する。試用は新規DBのみ。過去に旧ポリシーで保存した状態・receiptをそのまま新ポリシーで復元できる保証はなく、ポリシー変更を本番適用するならバージョンと移行の設計が必要である。

配布物検査はさらに、SQLiteの予算version比較を一時的に削除した負例を実行し、残額が同じでもversionが違う取得値を拒否する契約試験が失敗することを確認する。通常の成功試験だけで競合検出を保証したことにしない。


## 導入コストと型注釈

今回のファイルの物理行数（空行・import・コメントを含む）は、JSX側`application.tsx`が52行、明示的な接続の`plain.ts`が33行。書式に左右され、含む機能も異なるため、複雑さや生産性の順位ではない。少なくとも「この例では宣言的にすれば総行数が必ず減る」という説明はしない。

閾値変更で追加・変更した型注釈は両実装とも0。初期構成では、Koyuki側に四つの具体的なRequest型、Repository・ActorのContext、ResourceとOperationの対応が必要だった。通常TypeScript版にもRequestのgenericと戻り値のエラーUnionが必要。利用者がキャストを追加しなくても使える公開入力と閉じた成功・失敗の型を、生成宣言でも検査する。

選択の理由はこの行数差ではなく、実行通知と内部ルールのtrace、型付きイベント接続、構成時の不正検出、Providerによる業務部品のスコープを同じ実行器へ委譲できることにある。必要ないシステムではplain版の小ささが利点になる。
