[講演の対応表](../lecture-coverage.md)を、保存済み字幕へ戻って細かく点検するための記録。
自動字幕を読んだ結果の要約であり、逐語録・登壇者の監修・音声付き全編視聴の記録ではない。
字幕そのものはリポジトリへ転載せず、ファイル名・SHA-256・時刻区間と独自の評価を残す。

## 読み方

- supported：その論点に対応する実装・検証例がある。講演全体の完全実現を意味しない。
- partial：一部は対応するが、明示した制限が残る。
- gap：コードへ落とせる論点に対し、現時点のAPIに不足がある。
- design-choice：設計・適用範囲の判断。特定の機能を追加すれば完了する話ではない。
- experience：登壇者の経験・評価。Koyukiの実測値に置き換えない。
- context：導入・挨拶など、業務機能へ変換しない箇所。

evidenceは実装やテスト・設計判断へ戻るパスであり、そのファイルの存在だけで評価が正しいと証明されるわけではない。
review内に照合時の実装基準や同時に加えた変更を記録する。コードが変われば、意味の対応は再レビューが必要。

## 再現

```sh
npm run check:lecture-audit -- /path/to/functional-business-talks
```

検査するもの：保存済み字幕のhash・行数、区間の連続性、各字幕行がちょうど1つの話題へ割り当たること、
根拠ファイルが存在すること。
**検査しないもの：字幕の正確さ、要約の妥当性、全発話・画面の網羅、実装完了。**
字幕のない区間にも話題の時刻範囲が続くが、その間の音声や画面まで確認できたという意味ではない。
字幕行の割り当ては「講演内容の100%を実装した」という数値ではない。

## 2本目で明確にした不足と判断

29:09–29:36のループ内のResult処理は、従来の対応表ではcollect・withInputと一括りにしていた。
collectは固定フィールドのRecordを対象とするため、照合時点では専用の可変長の合成が不足していた。
その後[collectEachと明細の例](../collection-validation.md)で、同期の独立検証・全エラー収集を追加した。
入力順・要素位置・出力型・エラー型・集計と保存の停止を検証している。
最初の失敗で止める要素間の依存処理や、非同期I/Oの列まで自動化したわけではなく、対応は部分的と記録する。

30分台の開発速度・障害・教育の話は登壇者の経験。Koyukiの速度やバグ率を保証しない。
32分台のplain dataの利点も、公開する項目の選別や秘密情報の除外を不要にはしない。
言語レベルのdo記法や理想の言語に関する議論は、TypeScriptの構文を追加する実装要件へ読み替えない。

## 3本目で明確にした限界

23分台の状態の観測に対し、Koyukiのtraceは段階名と成否、Applicationはsnapshotを提供する。
**全段階の入力・出力のdumpや永続的な全状態履歴は、自動では記録しない。**
値の履歴を残す場合は、取得する段階・保存先・公開項目・保持の方針まで設計する必要があり、
既存traceがそれらを満たしたものとは扱わない。

35分台のResultの説明は、戻り値に表した想定内の失敗のモデルとして対応付ける。
TypeScriptの関数がResultを返す注釈だけで、throwやPromise rejectionが発生しないことまでは保証されない。
コアは予期しない欠陥の例外を伝播し、Applicationではcrashedと想定内のfailedを区別する。

再帰・reduceの総和の例は、計算の捉え方の説明であり、すべてのループ・ローカル変数・クラスを禁止する要件ではない。
39分台の継承の議論も、差分を目的とする安易な階層化への注意と、継承そのものの禁止を区別する。
29分台・40分台で説明を省略した箇所があり、その画面や後日公開資料の全内容は未確認のままとする。
