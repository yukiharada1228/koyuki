# 検証済みの証明を加えても、後段の要求型を推論する

[共通検証の後の要求型](business-later-request.md)の推論を、成功時に入力型Tへ検証済みの証明を加える関数にも適用する。先頭の関数が単にTを返す場合だけでなく、`T & Validated`等を返す場合も、loadの型引数を操作ごとに書かずに接続できる。

## 経費課題への適用

[AI試用から得た複数段の実装](../scripts/fixtures/onboarding-staged-solution.ts)も、共通検証を次の契約へ変更した。

```ts
const checked: unique symbol = Symbol('checked');
type Checked<T> = T & Readonly<{ [checked]: true }>;
```

commonはactive・versionを検証して`Checked<T>`を返す。submissionとapprovalは`Checked<Loaded<要求型>>`を受け取り、状態と権限を検証する。業務の状態生成も、前段が作った準備済みの文脈を受け取る。

共通loadと`[common, submission, submit]`等の関数列を宣言する形は変わらない。証明は業務関数が通常のTypeScriptで定義し、framework用の新しいAPIや設定は不要。共通検証を配列から省略すると、後段の要求する証明が存在せず、型検査で拒否される。

この証明は一時的な業務文脈にだけ加え、保存する経費モデルは従来のまま。以前の試用記録を初見の再評価として数え直すのではなく、AI試用で見つかった負担への後続改善として扱う。

## 接続の条件

先頭関数が入力の文脈と宣言した出力の事実を同時に保持することを、型の比較で確認する。独立した新しいプロパティを持つ文脈でも同じ保証が成立するかを追加検査し、Tを入れ子の中へ入れただけの出力を、元の文脈全体の保持とは扱わない。

読み込みが要求型と文脈全体を保証すること、各段階が前の段階の実際の出力を受け取れることも引き続き検査する。要求の特殊化に際して、loadの出力へ検証・権限の証明を足すことはない。

比較は関数自身が宣言した入力条件の範囲で行う。共通検証が「actorがあること」だけを要求する場合も、ロード結果の全体型へ関数の制約を狭める必要はない。

型の比較は関数の宣言した契約に対する検査であり、任意の実装の純粋性や業務仕様を証明するものではない。具体的なルールの内容には、業務テストを併用する。

## 利用者のモジュールをexportする

通常の型検査だけでなく、利用者側のAPIを戻り型の注釈なしでexportし、宣言ファイルを生成するところまで検査した。従来のCallableの型表現は、通常の型検査が通っても、内部のPlainCommand等を公開されていないsubpathから参照しなければ名前を付けられず、宣言生成に失敗する場合があった。

Callableは同じ2つの公開メソッドを直接表す形に修正した。実行時の処理、メソッドの型、公開API名は追加していない。

[利用者側のexport例](../scripts/fixtures/business-verified-exports.ts)では、loadのエラー型がgenericなfactory、そこから生成した定数、通常・再送・任意切替の3モードを含める。[宣言検査](../scripts/check-exported-business.mjs)は実tarballのSDKを使い、生成した.d.tsだけを別のconsumerから読み直し、要求・成功・エラー型を確認する。Node型は読み込まない。

以前の型表現へ戻す対照は、同じ利用者ソースの通常の型検査を通り、宣言生成だけが失敗することを確認する。生成時に別々に出力された同形の要求型についても、各モードで必須項目を厳密に保っていることを検査する。

## 検査と限界

[専用テスト](../src/business-verified-request.test.ts)では、検証済みと権限確認済みの2つの証明を分け、次を検査する。

- 共通／操作別loadから、要求・成功・失敗を厳密に推論する。
- 名前付きStep、通常・詳細・選択capture・再送でも同じ接続を使う。
- 検証失敗、権限拒否、業務判断の失敗で後続と保存を止める。
- 保存済みの再送結果を返す場合は、load・業務関数・saveを再実行しない。
- 検証・権限確認の省略、順序の逆転を拒否する。
- 広いloaderとの動的選択、入力項目を落とす関数、Tを別フィールドへ入れるだけの関数による誤った精密化を拒否する。

配布物検査にも同じテストを含める。証明を加える関数への対応を外すと、新しい正例が型検査で失敗することも確認する。

経費課題の配布物検査では、1段の従来実装、操作別load付きの複数段実装、共通loadだけの複数段実装が同じ13件の業務テストを通る。共通検証の省略は、型が合う業務条件の削除とは別の対照として拒否する。

外側のgenericなactor型との相関を持つ等の複雑なfactoryでは、検証関数を具体的な文脈型へ特殊化する記述がなお必要になる場合がある。任意の多相変換を解決したものではない。

実行runtimeや公開APIの追加はない。名前なしinlineや一般の深いgeneric変換、原音等の未確認部分は別の残件であり、講演全体の完全実現を主張するものではない。
