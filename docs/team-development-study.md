# チーム開発の標準化を検証する

Koyukiの価値仮説を「業務の型・検証・遷移と実行境界を、一貫した方法で実装できること」と置く。
関数の接続の省略やコード量だけでOSSの有効性を評価しない。
「React for Business Logic」は方向を表す表現であり、React相当の実績や普及を証明するものではない。

## 現在の証拠と仮説

| 論点 | 現時点の確認 | まだ主張しないこと |
| --- | --- | --- |
| 型による接続 | 入出力・検証済み証拠・失敗Unionの検査、外部consumerで不正定義を拒否 | 業務仕様の正しさ、型assertionまで含めた不正実装の完全防止 |
| 実装方法の統一 | UseCase / Group / Applicationの共通実行契約 | 100人の組織での教育効果・設計のばらつきの削減率 |
| 純粋関数のテスト | 経費・休暇・在庫の業務テストをIOから分離 | 通常のTypeScriptでは同じ分離ができないという主張 |
| 再送 | receipt境界、要求の一致、CAS、保存とreceiptの原子性を実例で検証 | どのadapterでも二重実行が起きない、任意の外部副作用のexactly-once |
| 実行履歴 | in-process traceと詳細report、observer、サンプルのDB履歴 | 永続監査ログの自動提供、traceが障害時にも必ず残ること |
| 移植性 | コアのWeb標準API・実行時依存ゼロ・Node型不要を配布物で検証 | 各サンプルのSQLite / Prisma / GraphQL依存までゼロという主張 |
| AI生成との相性 | 宣言の形と型検査を生成コードへ適用できる | AI生成の品質・正答率が実測で改善したという主張 |

## 比較対象

通常のTypeScriptでも共通化はできる。以下の三つを用意する。

1. 普通のservice関数で実装する版。
2. TypeScript＋Result＋小さな共通helperを使う版。共通化を禁止しない。
3. 現在推奨するKoyukiの宣言とruntimeを使う版。

比較する業務・境界の意味は同じにする。domain、入力例、認証情報、DB、外部API、障害注入条件を共通化する。
framework側にだけ再送・traceを付けた状態で、同等機能のLOCとして比較しない。
差がある場合は機能カバレッジの差として別記する。
共通helper、設定、adapter、テスト、生成物、coreの導入コストを分けて記録し、都合のよい部分だけを合計しない。

## 既存の小実験を再点検した結果

`npm run compare`は予約と注文の旧JSX実験であり、現在推奨するKoyuki APIの評価ではない。
共通helper版TypeScriptの2行のarrow関数を以前の計測が除外していたため、計測へ追加した。
現在の宣言範囲の物理行数は次のとおり。

| 旧実験の実装 | 操作2件の宣言 | 専用の共通helper | 範囲合計 |
| --- | --- | --- | --- |
| inline TS | 11 + 11 | 0 | 22 |
| helper TS | 2 + 2 | 12 | 16 |
| JSX | 3 + 3 | 16 | 22 |

この範囲ではhelper TSが短い。imports、組み立て、共有kernel・domainは上の合計に含まれない。
旧実験の61テストは3方式の成功・失敗等を検証するが、大規模開発・認知負担・実運用の比較ではない。
スクリプトは宣言ごとの出典行と、ファイル全体の行数・SHA-256も出し、再点検できるようにする。

`npm run compare:tags`は古いfeature.tsxへの参照が壊れていた。
現在のevents.tsの純粋な宣言に直し、Application・再送・trace・IO登録を比較していない範囲と明記した。
この計測から大規模アプリの総コストを推定しない。

## 次の実装対象：購買から支払記録まで

既存の経費・在庫・承認の経験を使い、つながった業務を一つのアプリとして構築する。
以下は評価用仕様である。[25操作の初期実装](procurement-study.md)を実装済み。[SQLiteの複合保存と復元](procurement-sqlite.md)を検証済み。[複合Application投影](procurement-projection.md)も検証済み。[永続再送境界](procurement-replay.md)も接続済み。[25操作の業務接続比較](procurement-comparison.md)を追加し、メモリ／SQLiteで3方式の結果一致を検証した。[基本traceと保存計画](procurement-trace-comparison.md)の代表ケースも一致を検証済み。再送・値の観測・Applicationを含む同等機能比較と変更評価は未実施で、評価完了ではない。

| 業務 | 操作候補 | 件数 |
| --- | --- | --- |
| 購買申請 | 作成・変更・申請・取り下げ | 4 |
| 承認 | 承認・却下・差し戻し・担当変更 | 4 |
| 発注 | 発注・変更・取消・完了 | 4 |
| 入荷 | 検収・返品・訂正 | 3 |
| 在庫 | 引当・解除・移動・棚卸調整 | 4 |
| 請求 | 登録・照合・承認・無効化 | 4 |
| 支払記録 | 記録・取消 | 2 |

計25操作を最初の規模とする。分納や複数明細は入力・状態で扱い、同じ関数のコピーで操作数を水増ししない。
100操作や100人での実績とは扱わない。最初は申請→承認→発注→入荷→請求照合の一連の経路を通す。
認可、予算、数量、金額、取消可能な状態、二重入力、要求ID、versionのルールを実装前に固定する。
外部の実決済・実メールは行わず、決定的なtest adapterを使う。

## 仕様変更で比較する

同じ変更依頼を各方式へ適用し、正しい結果になるまでの差分を記録する。

| 変更 | 観察すること |
| --- | --- |
| 承認金額の境界と承認段階を変更 | domainと業務テストだけで済むか。通常TS側も同じ分離を認める |
| 新たな認可失敗・エラーを追加 | 入力・失敗Unionとtransportの対応を型検査がどこまで検出するか |
| 履歴・再送境界の共通方針を変更 | 操作数に比例して接続を直すか、共通境界だけで済むか |
| 返品後の在庫・請求ルールを変更 | 複数業務にまたがる正当な変更と、定型接続の変更を区別できるか |

修正ファイル数だけを勝敗にしない。1ファイルへ詰め込んだ実装が有利にならないよう、
変更した業務規則・宣言・adapter・共有helper・テストの箇所数とdiffも残す。
仕様変更時間は、同じ人が二度目に解く学習効果を含むため、独立した参加者なしに速度優位とは主張しない。

## 測定と判定

- 同じ業務シナリオ・障害シナリオの適合率と、仕様上期待した永続状態。
- 業務規則・接続・adapter・共有基盤・テストを分けたソース量。
- 仕様変更の差分と変更箇所。生成物とlockfileはコード量から分ける。
- 故障注入時の停止・競合・再送・不明commitの結果。
- 型検査で拒否した誤接続と、実行時テストが必要だった仕様誤り。
- 独立した利用者のオンボーディング・レビュー結果を、得られた時点で別途記録。

故障注入を「実運用のバグ発生率」と呼ばない。テスト本数を品質点やバグ率へ変換しない。
現段階のバグ発生率・チーム生産性・AI生成改善率は未測定。
結果が同等・不利でも保存し、追加APIはこの実装で繰り返し現れた問題を根拠に検討する。
講演で述べられた標準化の構想に対応する、実装と評価を並行して進めるための方針とする。

## 利用者向けAPIの再検討

利用者の指摘を受け、購買アプリの実装着手に先立ち、
[普通の関数配列と直接呼び出しの試作](business-api-study.md)を経費の既存5操作で検証した。
role別の宣言は必須にせず、操作別の入力型・再送境界を保持する。
公開APIの追加は行わず、現行APIとの差分と残る制限を記録する。

続いて休暇の3操作でも同じ記法を検証した。未公開の候補パッケージを独立consumerへインストールし、
既存HTTP/GraphQL/Applicationとの接続・旧宣言との比較・SQLite移行の計31テスト、配布型の入力/接続拒否を確認している。
これはAPI改善の実現可能性の証拠であり、大規模チームの評価は上記の比較仕様のまま未実施。

[小さな仕様変更の比較](business-change-study.md)を実施した。
休暇承認の制限追加では4方式とも接続漏れを型で検出し、既存API・TS helperも局所的な変更で対応できた。
新APIだけが修正範囲を大幅に減らすという結果ではない。純粋な判断部分の比較と、Koyukiのtransport/replay連携の検証を分けて記録している。
