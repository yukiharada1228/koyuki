# 経費精算課題をAIが実装して評価する

ユーザーから協力者の代わりにAIが評価するよう依頼を受け、開発版の実tarballを使って申請・承認・却下を実装した。Koyukiの開発履歴を知る保守者側AIの評価であり、初見の独立利用者や人間の学習負担を測ったものではない。人間の試用を実装継続の条件にはしない。

参考解答は実装作成時に読まず、課題のREADME、contracts、host、最小APIガイドから書いた。実装後の回帰検査では、既存の参考解答も機械的な比較対象として実行する。所要時間、利用者の満足度、生産性の点数は計測していない。

## 実施と結果

配布物の基準はfe0737d023ac4c2cf8701a70fc4c39b03c87a1bb。[実装](../scripts/fixtures/onboarding-staged-solution.ts)は共通検証、状態・権限検証、状態生成を分け、submit/approveは3段、rejectは4段にした。`createExpenses`の最終API型を注釈で固定せず、提供テストの厳密な入力・成功・失敗型の比較で推論を確認した。

1. 共通のgeneric検証を全操作の先頭に置き、共通loadだけで宣言した。申請のapproverIdと却下のreasonが要求型に反映されず、型検査が失敗した。操作内の接続エラーと、呼出し側・結果型の二次的なエラーが同時に出た。
2. submitとrejectのloadに、それぞれ`ports.load<SubmitInput>`、`ports.load<RejectInput>`を指定すると型検査が通った。共通の検証・load/save実装は複製せず、接続callbackも追加しなかった。
3. 元のテストは13件中11件成功、2件失敗だった。失敗の原因は業務の誤りではなく、traceの件数が業務関数1個を前提に固定されていたことだった。
4. 成功時はload・1個以上のRule・saveが観測されて全て成功すること、Rule失敗時は最後が失敗し保存しないことを検査するよう、課題側を修正した。修正後は13件全て成功。最終実装の型検査はTypeScript 6.0.3と7.0.2で成功した。

この修正は参加者が自由に提供テストを変えてよいという意味ではない。保守者が課題の不備を訂正したもの。元のテストと初回実装はローカル評価フォルダーのevidenceへ保存した。

## 書く必要があったもの

| 項目 | 今回の実装での観察 |
| --- | --- |
| 業務関数 | 共通検証、申請の前提、承認の前提、却下理由、3つの状態生成の計7関数 |
| 通常の型宣言 | 上記7関数の入力・Result戻り型。Loadedのcurrentを絞った状態を表すReady型1個 |
| 接続のための明示指定 | 操作別loadの型引数2箇所。先頭が共通generic検証の場合に必要だった |
| 最終API型の注釈 | なし。createExpensesの引数Portsは外部境界の契約として明示 |
| any／型アサーション | なし |
| Resultの手動伝播 | なし。ifは業務条件の判定であり、前段Resultの成功値を取り出す接続ではない |
| I/Oの手動接続 | なし。load/saveは参照を宣言し、順次呼び出していない |
| 操作順の宣言 | 3・3・4個の関数列。検証の優先順は利用者が記述 |

## 改善点と判断

- **課題の不備は修正済み。** 単一Ruleへ業務を詰め込む誘導をなくした。既存の1段実装と今回の複数段実装を同じ配布物検査で実行する。
- **型推論の制限は残る。** 最初のRuleが操作固有の要求型を持つ場合と、共通generic検証から始める場合は異なる。今回の2箇所の型指定は後者の実測例であり、常に不要／常に必要とは一般化しない。最小APIガイドへ例を追加した。
- **接続エラーには位置情報があるが、診断が連鎖する。** 最初にapplication内の操作・段階を確認すると修正できた。人間にも理解しやすいことの証明ではない。
- **業務条件の正しさはテストが必要。** 共通検証を省略すれば型が合う場合がある。今回もinactive拒否を削る変異は型検査を通り、業務テストが拒否することを確認する。型による接続保証と仕様の正しさを分ける。

再現は`npm run test:onboarding:package`。未実装starter、1段実装、複数段実装、3個の業務条件の変異、2個の型接続の変異、準備時の上書き拒否を検査する。AI評価は今回の課題の具体的な改善根拠とし、講演全体の完全実現やReact/Elmと同等の開発体験が証明されたとは扱わない。
