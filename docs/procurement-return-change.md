# 仕様変更比較：移動済み在庫の返品・入荷訂正

二段階承認に続く2件目の業務仕様変更として、返品・入荷訂正が複数の保管場所へ及ぶケースを検証する。
基準commitは`f6fd925`。講演者の製品仕様を再現するものではなく、購買サンプルに対する評価用の仕様である。

## 仕様

```ts
const policy = {
  requestLimitCents: 2000,
  approverIds: ['approver'],
  receiptDepletion: 'available-locations',
} satisfies Policy;
```

既定の`receiving-only`は、従来どおり入荷場所receivingだけから在庫を減らす。
設定を省略しても動作は変わらない。新しい`available-locations`では次の方針を使う。

- 返品と数量を減らす入荷訂正では、receivingを優先し、その後は保管場所名のコード単位順に未引当分を減らす。
- 入力・DBの行順によって優先順位を変えない。既存のpositions配列の行順自体も入れ替えない。
- 引当済みの数量は残す。全保管場所の未引当分でも不足するならInsufficientStockで、全変更を拒否する。
- 新規入荷と数量を増やす訂正は、従来どおりreceivingへ加算する。
- 注文・入荷・照合済み請求書の登録状態への戻し・在庫は、既存の単一Changeと保存transactionで扱う。
- 承認済み請求書がある場合に返品を止める等、従来の権限・状態・数量規則は維持する。

これはSKU単位で在庫を代替可能とみなす仕様である。
特定の入荷lot・シリアル番号・棚の現物・原価・配送や実際の仕入先返送を追跡するモデルではない。
物理的にどの商品を返すかを、この台帳モデルから保証できるとはしない。

## 設定と履歴

方針は認証情報と同じくhostから渡し、context構築時にコピーする。
要求にreceiptDepletionという追加フィールドがあっても、hostの設定を上書きしない。
未認識の方針で返品・訂正を実行する場合はInvalidInputとし、別の方針へ黙って切り替えない。

方針は入荷Entityへ保存せず、操作を実行するclientの構築時の設定を使う。
したがって、新しい設定を渡したclientは既存の入荷にも新方針を適用する。
進行中の承認経路を申請時に保存する二段階承認の仕様とは、この点が異なる。
一方、receiptに保存済みの過去要求は当時の結果を返し、設定変更で再計算しない。
古い訂正要求を後からreplayしても、現在の返品済みEntityを巻き戻さない。

## 変更箇所

| 分類 | 変更 | 理由 |
| --- | --- | --- |
| domain.ts | Policyへ任意の方針を追加 | hostが業務方針を選ぶ |
| context.ts | 方針をコピーし、入荷のRule入力へ渡す | 要求から設定を受け取らない |
| inventory.ts | 純粋な在庫差分の生成 | 複数場所の未引当数量を決定的に減らす |
| 読み込み試作 | context-process.tsとcontext-application.tsも方針を伝える | 詳細loaderでも同じRuleを使う |
| 3方式の操作接続 | application.ts・plain.ts・helper.tsは変更なし | 既存のload→Rule→saveを使う |
| core・保存・再送 | 変更なし | 既存のCAS・複合保存・receipt境界を使う |
| 保存形式・復元 | 変更なし | Entityの形を増やしていない |

業務方針の選択と在庫の引き方はdomain側に残す。
Koyukiのruntimeが在庫規則を知ったり、transaction対象を自動推定したりする変更ではない。

## 検査

[22テスト](../src/procurement-return-change.test.ts)を、rootと実tarballのconsumerで実行する。

- Koyuki・通常TS・共通helper × メモリ・SQLiteで、訂正減算→訂正加算→返品を実行し、結果と全6モデルを比較。
- receivingより後に作ったalpha/betaの行順と処理順を区別し、未引当分の消費順と引当保護を確認。
- 既定方針、要求からの設定注入の無効性、構築後の設定変更からの独立、未認識設定を確認。
- 複数SKUの後半で不足しても、前半の変更や請求書の状態戻しが残らないことを確認。
- 各方式のSQLiteで在庫保存に例外を注入し、注文・入荷・請求書・在庫がrollbackすることを再開後も確認。修復後の明示再実行で成功。
- 別SQLite接続が引当を保存した後では、古い返品計画をCASが拒否する。新しい読込みでも不足を拒否し、引当解放後に成功。
- 各方式の永続receiptを再開し、設定変更後の過去訂正が当時の結果を返し、現在の返品済み状態を変更しないことを確認。
- 詳細loaderでも方針を渡し、内部取得traceを保持した訂正が同じ在庫Ruleへ接続することを確認。

3方式が共通のdomainとadapterを使う条件での比較であり、独立した設計・実装者の調査ではない。
この変更でも3方式とも操作接続を変更せず対応できた。
これをKoyukiだけの優位、一般的な修正箇所数・学習負担・生産性・障害率の改善とはしない。
高負荷・別OSの同時writer・他DB・lot管理・実際の倉庫運用の検証は今回の範囲外である。
