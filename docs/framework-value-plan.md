# Koyukiを選ぶ理由を検証する改善計画

目的は、関数型の業務の核とReact経験者向けの部品合成を保ったまま、実装方法の統一・接続の型安全性・運用境界の再利用を、比較可能な証拠で示すこと。人気や普及を実装だけで達成したと扱わない。

受入れ条件:

1. 既存経費モデルを使う代表例: 申請・上長承認・経理承認・差し戻し・編集再申請、予算確保と解放、通知・監査・再送を一つの公開APIの構成で扱う。
2. 予算超過・競合・途中保存失敗・応答喪失・再送・配送失敗を検証し、保存アダプターの契約を別アダプターにも適用できる形にする。
3. 同じ純粋関数とRepositoryを使う通常TypeScriptの実装と同じ受入れ試験で比較し、変更箇所・接続コード・型注釈と、Koyukiの追加コストを記録する。コード量だけで優位を決めない。
4. 業務拒否・入口の認可拒否・想定内の保存失敗・想定外の不具合を、実行通知とイベント配送でも区別する。
5. 学習ガイドを普通の業務関数→Workflow→Operation→JSX部品の順にし、保証範囲・適さない用途・公開実験APIの制約を明示する。
6. 公開importだけの配布物で型検査・宣言・実行を確認し、実行時依存ゼロとWeb標準ランタイムを維持する。

機能追加数やテスト件数を目標にしない。未達を個別に残し、この計画全体を満たすまで目標を完了扱いにしない。人間の協力者は必須条件にせず、AI試用と人間の利用評価は区別する。

## 2026-11-27 完了監査

この計画でいう達成は、採用判断のための具体的な実装・比較・保証境界が揃うこと。普及・人間の生産性・全用途での優位は主張しない。

最終結果:

- `npm run check`: 成功。
- `npm test`: 1332テスト成功。
- `npm run test:expense-budget:package`: TS7.0.2 / TS6.0.3の型検査・宣言生成・宣言consumer、11実行テスト、予算version負例、両実装の閾値変更試用に成功。
- `npm run test:connections:package`: TS6/7と45実行テスト、既存の型精度・view・イベント接続の負例に成功。
- `npm run check:package`: 実行時依存ゼロ、31ローカルJSモジュール、Node型なしの公開宣言を確認。
- `npm run test:portable`: Nodeグローバルなしのブラウザ実行に成功。
- `git diff --check`: 成功。

変更の採用理由は、独立した業務関数を保ちながら、型付き接続と実行・配送・認可・観測の契約を共通化できること。比較結果が同等の部分を隠して「常に簡潔」「必ず速い」とは説明しない。公開済みnpmとリモートCIは更新していない。
