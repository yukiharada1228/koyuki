# 有限モデル検査の限定採用判断

Issue #7の保守コスト・追加価値・採否を、経費の実験に限って評価する。
作業時間、バグ率、独立利用者の生産性は測定していない。
以下はコード・実行結果に基づく技術判断であり、一般的な導入効果の実証ではない。

## 型・個別テストに対する追加価値

[経費の既存検査](../src/expense-state-exploration.test.ts)は、有限の承認過程の
37状態・1,776操作を比較し、終端からの再承認と自己承認の拒否を確認する。
編集を含めると版数が増え続けるため、深さ7の探索はlimitedとして返す。
反例は初期状態と操作列を保持し、どの状態から結果が違ったかを確認できる。
個別テストで既に確認した自己承認を、初めて発見した不具合とは数えない。

[追加の変異検査](../src/expense-model-adoption.test.ts)は、金額3001の申請時だけ
操作者を無効に誤変換する、型の合う実装を比較する。完全な状態キーを与えると、
金額3001の初期状態から一回のsubmitで不一致を検出する。
型が合うことと業務の結果が正しいことを区別する具体例である。

一方、キーを状態のkindだけにすると、金額3000と3001のdraftが統合される。
同じ誤実装でも2状態・96操作の探索がpassedとなり、不具合を見逃す。
これは検査器の正当な利用例ではなく、キーの同値性契約を破った対照実験である。
passedの表示だけで、抽象化や業務全体が正しいとは判断できない。

## 実際に保守するもの

参照仕様は実装のvalidator・遷移・保存条件から独立して記述する。
仕様変更時には、同じ誤りを複製せず、両方を別々に見直す必要がある。

| 対象 | 見直しが必要になる変更 |
| --- | --- |
| 状態・期待出力と参照遷移 | 承認経路、金額境界、拒否の優先順位の変更 |
| 初期状態・イベント候補 | 役割、有効性、理由、入力境界の追加 |
| keyと抽象化 | 将来の挙動に影響する状態・証跡・版数の追加 |
| 実装との照合 | 入出力の形、保持すべき状態、対象の実行境界の変更 |
| 不変条件・探索上限 | 禁止する状態、循環、新しい段階、探索量の変更 |

現在の[共有契約](../src/expenses/model-testing.ts)は117物理行で、有限探索・seed付き検査・
雛形生成の間で共有する。参照関数は30行、keyは2行、実行関数と照合関数は計21行。
これは`61453d6`時点のソースの位置から数えた記述量で、保守時間の推定値ではない。
共有契約全体を有限探索だけの追加コストとはしない。
上のkey対照実験が示すとおり、短いキーでも意味上のレビュー負担は大きくなり得る。

## 判断

**明示した有限モデルを持つ業務向けの、任意の実験用testing入口として採用を継続する。**
通常の型検査・個別テスト・adapter契約テストと併用し、業務runtimeの必須宣言にはしない。
passedだけを単独の品質保証として使う方針は採用しない。

追加価値は、指定した組合せの探索と再現可能な操作列である。
追加負担は、独立仕様・抽象化・照合の保守と、その正しさのレビューである。
この負担を上回るチーム全体の工数削減や品質改善は未実証で、正式な一般推奨の根拠にはしない。
講演がこのAPIや採用判断を指定したという意味ではない。
