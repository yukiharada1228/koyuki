途中IOと独立した検証の合成

目的
動画の「IOの前後を純粋なワークフローに分ける」構造と、
複数のResultを組み合わせる負担を、小さな実例で検証する。

追加した核
collect({ field: Result, ... })
- 独立した項目の検証結果を受け取り、成功値を型付きのオブジェクトにまとめる。
- 失敗時はfieldとerrorの組をすべて返す。fieldごとのerror型の対応も保持。
- 引数の検証は呼び出し前に実行済み。collectが検証関数を実行するわけではない。
- 項目は通常の文字列キーのオブジェクトを想定する。
- 依存する業務判断は従来どおり最初の失敗で停止する。

process<Input>().through(workflow).effect(name, adapter).commit(mutation)
- 同期の純粋なworkflowと、IOを含むprocessを別のAPIにした。
- throughは純粋な計算、effectはPromise<Result>を返す明示的な境界。
- アダプターが、次の判断に必要な元の値と取得結果をまとめて返す。
- 途中の出力型・失敗型を接続し、全段階のtraceを返す。
- 組み立て時はIOなし。run/runDetailedで実行。processにはprepare/inspectなし。
- 各段階は一回のrunにつき最大一回。runを呼び直せばIOも再実行される。
- 自動再試行や全体トランザクションは提供しない。
- 予期しない例外は隠さない。想定する外部障害はアダプターでResultに変換する。

業務例
入力検証 → 注文取得 → 配送方法選択 → 外部送料見積もり → 金額検証 → 保存。
国内/海外の判断後に、その結果を使って見積もりを問い合わせる。
入力の3項目が不正なら3件の検証エラーを返し、IOは実行しない。
注文が終了済みなら見積もりを取得しない。
見積もり取得失敗・金額不正・送料超過なら保存しない。
保存時はexpectedVersionを検査するポート契約。並行実行では片方が競合になる例を検証。

比較
src/shipping/feature.tsに、同じルールとポートを使う通常TS版を併記。
21組の入力/障害条件で、結果とIOの呼び出しが一致。
通常TS版も短く読める。フレームワーク版の優位性は短さより、接続と失敗型、
traceの取得を共通化できること。大規模な変更容易性の優位はまだ実証していない。

検証
npm run check: 成功
npm test: 228件成功（追加19件、既存209件）
npm run demo:shipping: 成功。国内・海外・入力不正の3例で通常TS版と結果一致。
型テストで、誤った段階の接続、非同期関数を純粋なworkflowに入れること、
失敗型の欠落、検証済み状態の直接構築を拒否。
実行時テストで途中停止、選択した配送方法、実行順、例外の伝播、競合を検証。

範囲と限界
新しい送料例はインメモリアダプターによる検証。実際の配送API・DB・画面は未実装。
既存タグのSQLite/HTTPテストは回帰確認として成功。
送料見積もりの期限、外部サービスの契約検証、再送の冪等性、注文の実際の出荷は未実装。
型は純粋性やアダプターの正しさを自動保証しない。
途中IOは読み取り用途。外部決済等を入れたときの補償や複数保存の原子性は提供しない。
診断のtrace/planには入力が含まれ得るため、運用時のログ公開方針は別途必要。
JSXは不要だった。人間の承認待ちや永続ランタイムは今回増やしていない。
