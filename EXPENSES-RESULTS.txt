第2ドメインでの汎用性検証: 経費申請と段階的な承認

目的
タグで自動化した「状態・検証・遷移から、接続と実行を任せる」設計を、
別の業務にも新しいフレームワークAPIなしで適用できるか確認する。
Reactや画面は評価対象にせず、業務状態と実行の接続を検証した。

実装
src/expenses/domain.ts: 状態の直和・入力検証・権限検査・状態遷移。
src/expenses/application.ts: モデル境界の登録、イベントと操作の宣言、結果の反映。
src/expenses/repository.ts: version比較つきの単一プロセス検証アダプター。
src/expenses/demo.ts: 申請者→上長→経理で同じ保存状態を進める実行例。

業務状態
Draft | PendingManager | PendingFinance | Approved | Rejected。
経理承認待ちには、前段の上長の承認者IDが必須。
上長・経理承認済みの結果には、領収書確認と承認者の証拠を保持する。
成功した保存結果から次の表示/観察用状態を更新する。
業務状態のmanager/financeと、実行基盤のready/running/failedは別の軸。

ルール
3000円以下は自動承認。それを超えると領収書と上長承認が必要。
10万円を超えるとさらに経理承認が必要。
金額別の経路は既存のexpenseWorkflowを再利用した。
自己承認、別の段階の役割による承認、無効な操作者を拒否。
申請は本人のみ。却下には空白でない理由が必須。
最終状態からの追加承認・再申請は拒否。
承認は別の人から届く新しい外部イベントとして扱い、内部完了イベントは利用者が書かない。
これらの金額や権限は検証用の仮仕様であり、実在組織の規程ではない。

利用側で書いたもの
- 状態の直和と、状態に必要な証拠。
- 検証と純粋な状態遷移。
- どの取得・保存を使うか、認証済み操作者を注入するモデル境界。
- 成功した経費を業務状態の一覧で置き換える関数。

利用側で書いていないもの
- Resultによる小関数の手動合成。
- ロード→検証→保存の実行手順。
- effect、完了イベント、実行中/失敗への切り替え、失敗からの復帰のswitch。
- 申請/承認/却下ごとの個別ランタイム。
既存defineTarget/step/operation/defineApplicationで実装し、framework配下は変更していない。

検証
npm run check: 成功。
npm test: 279件成功（既存266＋13）。
npm run demo:expenses: 成功。EXPENSES-DEMO.txtに出力。
金額の境界、領収書、申請者/承認者/自己承認、却下理由、終端状態、
同じversionから準備した承認と却下の競合、標準ライフサイクルと復帰を検証。
6つの金額/領収書の条件に対して5操作ずつ、通常TSの直接Result合成版と比較。
30回の比較で、Result、IO呼び出し、保存状態が一致。
型検査で経理待ちの上長証拠欠落、未検証の承認、保存用Changeの直接構築、
異なるイベント間の接続を拒否。
既存のHTTP/SQLite/React等の回帰テストも成功。
画面とWebサーバーの機能追加は行っていない。ブラウザー検証も対象外。

発見したこと
この例では新APIを増やさず、タグと同じ標準形が使えた。
人間の承認のような時間をまたぐ業務状態も、保存状態と新しい外部イベントで扱える。
ただし一覧への結果反映、必要なデータの取得、信頼された操作者の取得は自動推測できず、
明示的な業務/境界定義として残る。
複数人のセッション同士の一覧同期も、自動的には得られない。
この検証は通常TS版との振る舞い比較であり、長期開発の生産性向上を実証したものではない。

限界
経費用の保存先はインメモリ。本番DB、再起動をまたぐ待機・再開は未実装。
デモでは各操作者の操作時に、現在の保存状態から新しいセッションを起動する。
actorはホストが認証済みとして注入するテスト用claim。実認証や部署別の承認関係は未実装。
アダプターは単一プロセスのversion比較のみ。分散トランザクション、イベント通知、
承認依頼メール、外部決済、冪等なイベント配信は提供していない。
保存済みドメイン状態とセッションの観察状態は別であり、実行状態を永続化したわけではない。
