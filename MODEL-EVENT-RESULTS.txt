モデルとイベント定義に集中する標準形

今回の到達点
現行のタグ作成・更新では、利用側でWorkflow.then、Resultの分岐、
ロード→判断→保存の接続を記述せず実行できる。
業務の順序は宣言し、その順序での実行・失敗の伝播・保存はフレームワークが担当する。
すべての業務に対応する汎用基盤を完成させた、という意味ではない。

実際の利用側
const tags = tagModel(repository);
const create = tags.creation.on(createTagEvent);
const update = tags.revision.on(updateTagEvent);
await create.run(input);
await update.run(updateInput);

業務イベントの定義（src/tags/events.ts）
createTagEvent = {
  validate: step('validate-create', validateCreate),
  require: [step('check-unique-label', checkUniqueCreate), step('check-quota', checkQuota)],
  evolve: step('create-tag', createTag),
}
定義は関数呼び出しの接続コードではなく、入力検証・必要条件・状態遷移の宣言。
requireの順序は業務仕様として残す。順序を推測して実行する仕組みは導入しない。
ここでいうイベントは受け付ける作成・更新操作の記述であり、完了済みのドメインイベントを
配信するイベントバスや、イベントソーシングではない。

責務の配置
1. ドメイン: 状態の直和・ブランド、検証、必要条件、状態遷移の純粋な関数。
2. イベント: validate/require/evolveの定義。
3. モデル境界: 操作ごとの取得・保存アダプターを一度登録（src/tags/model.ts）。
4. フレームワーク: 型付きの自動合成、ロード、途中停止、保存、実行記録。
5. Hono: HTTP入力とレスポンスへの変換。既存画面とSQLiteで新しい経路を利用。

単なる接続コードの移動との違い
従来: 利用側がworkflow.thenを組み、bindMutation/defineActionをつないでいた。
今回: transitionがイベント定義を解釈して合成し、target.onが実行を構成する。
IO登録には引き続き取得・保存の対応が必要だが、モデルの境界に一度置く。
同じtargetに別の検証ポリシーを持つイベントを定義しても、IO登録は書き直さない。
予約語を禁止する検証への差し替えをテストし、load/saveを変更せず利用できることを確認。
型は各段階の入出力、requireの隣接関係、最終状態と保存先の対応を確認する。
定義だけで業務関数を発見・生成したり、必要な状態を自動推測するものではない。

標準形の確認条件
- 利用側がResultの確認・伝播を書かない: 達成。
- 利用側がWorkflow.thenで小処理を手動接続しない: 達成。
- モデル境界の登録を利用してload/saveを各イベントに書かない: 達成。
- 入力と既存状態のコマンド化を各ハンドラーで繰り返さない: タグのloadUpdateが担当。
- 業務判断をIOなしで単独評価できる: transition(event).run/inspectで達成。
- 直和と段階のブランドを維持する: 達成。
- 必要条件の省略・順序の逆転・異なる保存先への接続を型で拒否: 達成。
- 通常TSや旧接続方式と同じ業務結果を保つ: 比較と既存テストで確認。

検証
npm run check: 成功。
npm test: 247件成功（既存241＋6）。
npm run demo:events: 成功（作成→更新→入力不正。入力不正時に保存しない）。
既存の旧接続比較テストは、旧workflow.thenを独立に再構築して比較するよう更新。
Result/trace/plan/IO呼び出し/最終レコードの一致を維持。
既存SQLite/HTTP/TCP/移行/競合の検証も新経路で成功。
型テストでイベントの取り違え、必要条件の省略・逆転、入力・失敗型の欠落を拒否。
別ドメインのカウンター例、空のrequire、同じイベントを別Repositoryに接続する例も確認。
UI変更なし。今回はブラウザー操作の再検証は行っていない。

残る責任と保証範囲
純粋性・仕様の正しさ・as/anyによる迂回は型だけでは保証しない。
保存時の競合検査・DBトランザクションはアダプターの責務。
永続的な人間承認待ち、イベント配信、分散実行、自動再試行、再送の冪等性は含めない。
複雑な途中IOはprocess等の低水準APIを利用する。
見積もり・経費・ライフサイクル等を全てこの標準形に一括移行したわけではない。
旧JSXのTagProcessや低水準mutationは比較実験の互換口として残す。
コード行数が全体で減ったという主張はしない。規約と型の実装はフレームワーク側で増えた。
価値は利用側が実行手順ではなく、業務の状態とルールの宣言に集中できること。
