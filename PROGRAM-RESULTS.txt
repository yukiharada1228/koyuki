React/Elm型の開発体験: 状態・イベント・表示・コマンドを一つの実行モデルにする

設計
JSXの記法を再現するより、まずElmのinit/update/view/commandの構造を採用した。
従来のモデル・イベント定義は単一業務操作を担当し、その上でprogramが
長く存在する状態、外部からのイベント、IOの完了イベント、表示モデルをつなぐ。

利用者の定義
init(): 初期状態と初期コマンド。
update(state, message): Result<次の状態とコマンド, 不正な遷移の失敗>。
view(state): 状態を表す純粋な表示モデル。
effect(name, adapter, completionMessage): IOを実行せずコマンドを組み立てる関数を定義。

ランタイムの責務
startで初期コマンドを実行。
dispatchでイベントを受け、updateの出力を採用。
返されたコマンドを実行し、完了イベントをupdateへ自動入力。
状態が変わるたび、viewを計算して購読者へ配信。
外部からのdispatchを直列化し、任意のexpectedRevisionで古い画面の操作を拒否。
コマンドとイベントの実行記録を保持。
一連のコマンドは直列で実行。100個を超える自動連鎖は異常として停止。

タグでの実例
ready → createイベント → creating → コマンド実行 → createdイベント → ready/failed。
updateイベントも同じ規約でつながる。
作成中/更新中の表示は自動で配信され、完了後は一覧の表示モデルが更新される。
業務エラーはfailedの直和の状態になり、dismissイベントでreadyへ戻る。
既存のdefineTargetとタグイベントが検証・保存を担い、別の業務エンジンに置換しない。
init/update/viewはランタイムを起動せず単独でテストできる。

実行
npm run demo:program
src/examples/tag-program.tsは端末表示アダプター。subscribeで表示モデルを受け取るだけ。
作成・更新・検証エラー・dismissまで状態と表示の自動変化を確認できる。
src/tags/program.tsがアプリ側の状態・イベント・update/view定義。
src/framework/program.tsが汎用のイベントループ。

検証
npm run check: 成功。
npm test: 256件成功（既存247＋9）。
npm run demo:program: 成功、出力はPROGRAM-DEMO.txt。
一度のdispatchからコマンド実行と完了イベントが自動連鎖すること、
中間表示・完了表示の配信、検証エラー、古いrevision、同時dispatch、
状態コピーの分離、初期コマンド、例外時のキュー継続、純粋関数単独実行を検証。
既存Hono/SQLite等のテストも成功。
ブラウザーUIの変更や再操作は今回は行っていない。

現段階で言えること
業務状態と表示とIO完了イベントをつなぐ一つの開発モデルができた。
タグ例では呼出側が完了イベントのdispatchや表示更新を手書きする必要がない。
React/Elm全体に相当する製品品質や機能を完成させた、とは言えない。
既存のHTTPタグ画面はまだprogramに接続しておらず、今回の表示アダプターは端末のみ。

保証範囲
単一プロセス・単一セッションのMVP。セッション状態・履歴はメモリ上。
DBに保存されたタグと、セッションの表示状態は別。
再起動後の自動再開、途中IOの耐障害性、分散ロック、exactly-onceは提供しない。
予期しないコマンド例外はdispatch/startをrejectし、採用済み状態は戻さない。
コマンド完了イベントをupdateが拒否した場合も例外として表面化する。
タグ例では予期しない例外でcreating/updatingに残り得るため、本番化には復旧設計が必要。
履歴は診断用で、巻き戻し/リプレイはない。
購読者の通知例外は他の通知とコマンドを止めない。購読側でエラーを扱う必要がある。
全メッセージは信頼されたアプリ内部用。未検証のHTTP要求をそのままdispatchしない。
ユーザー認証、外部/内部イベントの権限分離、利用者別セッション管理は未実装。
viewは表示データの宣言。DOM差分更新・コンポーネントのライフサイクルは提供しない。
モデル同士の合成、型付きフォーム/画面アダプター、永続化と復旧、DevToolsは今後の設計対象。
これらはメソッドを追加するだけで保証できず、実アダプターで別途検証する。
