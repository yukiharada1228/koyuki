3層版の再検証

コード: src/v2.tsx
テスト: src/v2.test.tsx
実行: npm run check && npm test
結果: 型チェック成功。旧版15件と新版14件の計29件成功。
旧版のWEAKNESSテストと新版のREMAINING/NEW LIMITテストは、弱点が再現されることを確認するテスト。

構造
1. decide(state,event): 純粋な状態遷移。既存のvalidate/confirmのResultを利用。
2. ReservationProcess(state): 副作用も関数closureも含まない、JSON化可能な処理宣言をJSXで構築。
3. RuntimeV2 + FileStore + Mailer: 宣言の実行、結果イベント、状態更新、実行記録の保存。

前回から改善を確認したこと
- JSX兄弟間の暗黙的な型接続を廃止。SaveにはCandidate、NotifyにはSavedを直接要求し、不正なpropsをコンパイル時に拒否。
- 純粋な遷移を外部操作の完了ビットでスキップしない。
- 保存対象、次の状態、結果イベント、実行記録、outboxを一つのsnapshotにまとめて保存。
- 保存直前に障害を注入すると全て旧状態のまま。復旧後に正常実行できる。
- ファイルを読み直してRuntime/Storeを再生成してもSaved状態から通知へ再開し、完了後の再実行では通知しない。
- 同じファイルを共有する2つのRuntimeの同時runで通知は1件。
- 同一コマンドIDの入力差し替え、古いrevision、状態と合わない宣言を明示エラーに。
- 同一空席snapshotから2件が確定候補になっても、保存は片方のみ成功。もう片方はconflict。通知は勝者のみ。
- 業務上の拒否、保存競合、インフラ例外、不正イベントによる実装不整合を分けた。
- 外部サービス失敗時はSaved状態と未送信outboxが残り、再試行可能。
- メール送信成功直後のクラッシュは、同じキーを重複排除する模擬プロバイダーとの組み合わせでは重複を抑制できる。

残った問題
- プロバイダーが冪等性を提供しない場合、送信直後のクラッシュで引き続き2回届く。outboxやロックだけでは解決しない。
- FileStoreのロックは同一Nodeプロセス内のみ。別プロセス、複数サーバーでは保証できない。
- atomic renameは単一snapshotの可視性のための試作で、fsync、電源断、実DB、別ストレージとの原子性は検証していない。
- 実際のプロセスkillではなく、例外注入とRuntime/Store再生成による復旧テスト。

今回新たに発見した弱点
- 外部IOの間もストア全体をロックしている。遅いメール送信が別の予約の受付まで止めることをテストで確認。
  次の設計では短いトランザクションで操作をclaimし、IOはロック外へ出す必要がある。
  その際はlease切れ・二重worker・古い結果の適用をrevision/fencingと冪等性で扱う必要がある。
- 型の保証は今回用意した具体的なSave/Notifyコンポーネントの境界内。汎用の操作→イベント定義で関連する型を維持する設計は未実装。
- RuntimeV2は予約専用のswitchを持つ。汎用フレームワークとしてのoperation registry/typed adapterではない。
- JSXは現在1状態につき1操作の記述。ユーザー定義コンポーネントの合成、Sequence/Parallel、取消し、イベント遅延や逆順、長期承認、定義のバージョン移行は未検証。
- 現在のJSXはタグ付きオブジェクトを読みやすく返す用途が中心。Reactらしい合成が通常の関数より有利かはまだ実証できていない。
- operation identityはコマンドID＋revision＋操作種別。入力変更は明示的な別操作にする。フロー変更時の互換性は未解決。

判断
3層の分離は、状態喪失と副作用実行の混同を減らす方向として有効。
ただし「React的な宣言」という核を検証した段階であり、汎用コンポーネント合成や本番運用の保証は未達。
次の小さな検証候補は、型付きoperation registryと再利用可能なコンポーネント2種類を作り、普通のTS実装との記述量・理解のしやすさを比較すること。
永続実行はadapter契約に分け、まず汎用性と合成の価値を確かめるのが妥当。
