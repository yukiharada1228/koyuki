承認待ち・条件分岐・並列処理の比較結果

結論
「状態→現在必要な処理の宣言」という形は、待機と並列を扱うと意味が出てきた。
特に、承認待ちの種類や現在の並列操作を、実行せずに取り出せる点が明確になった。
ただし、追加承認の局所的な変更と重複防止は通常TS版でも同等に実現できる。JSXの優位性、チームでの読みやすさ、汎用フレームワークとしての完成はまだ実証していない。

実装
src/approval/domain.ts: 状態型、イベント型、純粋なdecide、金額による承認ルール。
src/approval/declarative.tsx: OrderProcess、FulfillOrder、WaitForApproval、Parallel、型付きCommit/Notify/Ship。
src/approval/backend.ts: 模擬の保存・通知・出荷アダプター。
src/approval/host.ts: ケースの状態・版、承認イベントの重複排除、操作実行と結果の反映。
src/approval/runners.ts: 宣言ツリーの解釈と、通常TSで同じ処理を書く比較版。
src/approval.test.tsx: 同じシナリオを両実装で検証、状態・結果・副作用の直接比較。
src/approval/demo.ts、APPROVAL-DEMO.txt: 二段階承認→通知失敗→通知のみ再試行の実行例。

再現
npm run check
npm test
npm run test:approval
npm run demo:approval

検証結果
型チェック成功。全128件成功（今回38件＋既存90件）。
問題が残ることを確認するテストも含む。

確認したシナリオ
- 少額の注文は承認なしで確定→通知と出荷依頼。
- 高額の注文は管理者承認待ちで停止し、待機中の繰り返し実行でもIOなし。
- 承認イベントで再開。承認待ちはPromiseやスレッドを保持せず状態として表現。
- 管理者や財務による却下では保存も通知も出荷も行わない。
- 追加財務承認ポリシーでは、10万円以上の注文に二つ目の承認待ちが入る。
- 金額の境界（9999/10000/99999/100000）を確認。
- 保存競合では通知と出荷を起動しない。
- メールだけインフラ障害になった場合、出荷成功を保持し、再試行ではメールのみ実行。
- 出荷だけ失敗した場合も、メールは再送しない。
- 並列の片方が先に失敗しても、もう片方の処理が落ち着くまで結果を返さない。
- 同じJournal/StateStoreを使う複数Hostの同時runで、外部操作を重複させない。
- 承認イベントIDの重複は再適用しない。同じIDの異なる内容は拒否。
- 過去の承認依頼への遅延イベント、別の役割、別の依頼IDは拒否。
- 状態版が古い内部更新は適用しない。
- ケース開始時のポリシーを固定。設定変更が進行中ケースを暗黙に変えない。
- 模擬プロバイダーの冪等性を使い、メール成功後クラッシュから再開しても重複配送を抑制。
- 両実装の状態、結果、副作用履歴が承認→追加承認→部分失敗→再試行を通じて一致。

仕様変更の比較
single-v1: 1万円以上は管理者承認。
double-v1: 上記に加え、10万円以上は財務承認。
この変更はdomainのnext関数とポリシーで表現。宣言コンポーネントと通常TSランナーのどちらも変更不要だった。
これは純粋な業務判断と実行を分離した利益であり、JSXだけの利益ではない。
進行中のケースのポリシー移行は未実装。新しいケースから新ルールを適用する。

React的な宣言から得られたもの
- stateがwaitingなら現在の承認依頼、committedなら現在必要な並列操作を返せる。
- FulfillOrderは「通知と出荷依頼」を組にする部品として親から利用できる。
- 処理宣言にはclosureやアダプターを含めず、現在のplanをJSON化できる。
- 外部操作を呼ばず、現在のplanを検査するテストを書ける。
- 前のProgram/flatMap版と違い、今回の現在planは関数を含まない。
ただし、将来の全状態・全分岐が一つの静的DAGになるわけではない。状態ごとに再評価するモデル。
通常TS版もdomainやdescribeを分離すれば同じ観察機能を追加できる。その分離を標準の契約にすることがフレームワークの候補となる。

残った弱点・新たに分かったこと
1. JSXの子要素の型は共通型に広がる。
   Notifyへ未保存の値を渡すことはコンパイルで拒否できるが、Parallelに待機ノードを混ぜることは実行時検査になる。
   同じ操作名の子を二つ置いた場合も、今回は実行時に重複識別子として拒否。一般的なkey/scopeは未実装。
2. 通知が業務上拒否された場合、そのResultは操作結果として記録される。
   設定を直してrunし直すだけでは再送しない。明示的な再送イベントや新しい操作版のAPIが必要。
3. 承認済みという構造型だけでは、承認の正当性を証明できない。
   approved-orderというオブジェクトを手で作り、アダプターを直接呼べば、必要な承認を飛ばせることを再現。
   通常のHost経路は防ぐが、厳密に守るなら非公開の構築境界・opaque型と復元時検証、ホスト側の権限境界が必要。
4. 待機ノードを表示するだけでは、承認依頼の通知や人の認証を実装したことにならない。
   actorRoleは信頼されたホストが与える想定の値。実ユーザー認証、承認者の権限・本人性は未実装。
5. 出荷とメールは独立して進むという今回の仕様を明示した。
   メールの失敗で出荷を取り消す仕様なら別の順序・補償が必要。Parallelはその契約を自動決定しない。
6. JSX/Planとinterpreterはまだ注文専用のOperation名・型を持つ。
   汎用の操作登録、別業務の待機コンポーネント、Hono接続までできたフレームワークではない。

実験の限界
Backend、StateStore、Journalはインメモリ。同じオブジェクトを使うHost再生成までで、OSプロセスの終了・再起動を越えた復旧ではない。
承認待ちを跨ぐ実時間や数日の経過は再現していない。イベントを後から投入する形で検証。
実DB、分散ロック、実メール、実出荷、電源断、ユーザー認証、承認期限、取消し、補償、定義の版移行は未実装。
外部成功後の重複排除は模擬プロバイダーの冪等性に依存する。
状態・実行結果・イベント履歴を複数の永続化先へ原子的に保存する保証はまだない。

次の設計判断
MVPの中心候補は「純粋なdecide」「副作用なしのdescribe」「型付き操作を実行するruntime」という3層の契約。
待機・並列・操作の識別子・結果イベントを汎用の契約へ抽出し、JSXはその宣言を組み立てる表現として位置付ける。
先に決めるべき点は、人の承認イベントを受ける境界と、失敗した操作を明示的に再試行する意味。
今回だけではJSXの採用を必須にする根拠はないが、状態から現在planを得る設計はMVPに残す価値がある。
