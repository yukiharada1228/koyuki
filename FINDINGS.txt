Business React Lab — 設計検証結果

目的
動画の型付き状態遷移・Result合成・IO分離を保ち、React風の状態→処理宣言→実行→イベント→状態というモデルを予約確定で試す。
これは設計検証用。実DB、外部メール、Hono、プロセス間の永続化は未実装。障害テストはインメモリの決定的な再現であり、実サービスの耐障害保証ではない。

実行
npm ci
npm run check
npm test

実装
src/core.ts: Result、型付き関数合成、独自JSX factory、Sequence/Parallel、最小ランタイム。
src/reservation.tsx: Raw→Validated→Checked→Candidate→Saved。純粋な検証・確定判断。version比較付き保存とoutboxをインメモリの同期クリティカルセクションで模擬。
src/lab.test.tsx: 正常系・業務拒否・競合・再試行・クラッシュ・重複・状態喪失。
src/types.test.tsx: 型付きcomposeが拒否する不正接続を、JSXの兄弟要素は許すことを検証。明示的な状態propなら同一境界内の型制約は保持可能。

検証結果
型チェック成功、15テスト成功。WEAKNESSテストの成功は「問題の再現に成功」の意味で、問題を解決したという意味ではない。

1. JSX兄弟要素の型接続の喪失（実証）
各要素のpropsは正しくても、前要素の出力と次要素の入力の関係は共通のJSX.Element型に消える。
compose(validate, confirm)は型エラー、Sequence内の不整合なTypedStepの組はコンパイル成功。
これは全JSX設計が不可能という証明ではない。今回の単純な兄弟要素APIでは保証できないという結果。
方針: 純粋な計算の接続は型付き関数合成で保持し、JSXには明示的に型付けされた状態・操作・イベント境界を渡す。

2. 外部成功と実行記録の間のクラッシュ（実証）
メール送信成功後、completed記録前にクラッシュすると再試行で2回届く。
外部送信側に同じキーを渡して重複排除できる模擬プロバイダーでは1回に抑制できた。
outboxだけで外部重複が消えるわけではない。事業者のキー有効期間・スコープも実接続では確認が必要。

3. 実行済み記録と状態更新の分離（実証）
保存とemitは成功したが次の状態だけ失われた条件では、同じcandidateを評価してもsaveがskipされ、Saved状態に戻れない。
方針: command処理・状態更新・必要なoutboxを同じ永続化境界で扱う、または結果を記録してイベントを再配信可能にする。keyの完了ビットだけでは不足。

4. 同時実行と再起動（実証）
completed確認だけでは同時実行2本が両方メールを送る。新しいRuntimeインスタンスでは履歴が失われ重複する。
方針: リクエストごとにランタイムを生成するHono統合ではインメモリ履歴を保証に使わない。永続ストレージで原子的なclaimや状態versionを扱う。ただしclaimだけでも外部成功後クラッシュ問題は残る。

5. 同じkey・異なる入力（実証）
同一keyでpayloadを変えても、新しい処理が黙ってskipされる。
方針: 業務上の操作ID・revision・入力の同一性を定義し、不一致を明示エラーにする。render回数を識別子にしない。

6. 空席確認と保存の競合（実証）
同じ空席snapshotを読んだ予約2件が両方業務判断に成功する。保存時の原子的version比較では片方のみ成功。
方針: Candidate（確定予定）とSaved（保存済み）を区別。ConflictをFullと一括にしない。実DBでの分離レベル・制約の検証は未実施。

7. JSXの順序と並列（実証）
Sequenceでは保存失敗でメールは未実行。Parallelでは保存失敗でもメールが実行される。
方針: Fragmentの意味を暗黙にしない。順序依存・並列を明示。Sequenceは原子性や外部操作の取り消しを保証しない。

設計の修正提案
A. decide(state,event)は同期の純粋関数で、Result<次状態,業務失敗>を返す。
B. describe(state)は操作の宣言を返し、評価中にIOを実行しない。
C. ランタイムは型付き操作をアダプターで実行し、型付きイベントとして結果を返す。
D. 純粋な遷移は「一度だけ実行する外部操作」のjournalに混ぜない。今回のdescribeはあえて両者をOperationに統合し、その弱点を露出させた。
E. 小さい計算の合成はTS関数側、JSXは業務単位の構成に使う。自動生成したイベントで細かな計算全てを表すと冗長化する。
F. 状態を永続化する範囲、operation identity、コミット境界を先に仕様化する。JSX文法の最適化はその後。

未検証
汎用的な型付きイベントdispatcher、操作→イベントの全体整合性、実DBトランザクション、ネットワークtimeout、分散claim、cancel、並列結果の順序逆転、長期承認待ち、ワークフロー定義のバージョン移行、性能、従来のTSとの記述量比較。

結論
React的な宣言・合成と動画の純粋な判断は併存可能。JSXを計算の暗黙的パイプラインにすると型が弱くなり、Reactの再評価をそのまま副作用実行と結ぶと重複と状態不整合が発生する。
次の実装は「純粋な遷移」「処理の宣言」「実行・保存」の3層を明示する。永続実行まで担当するか、ホストアプリ側の責務にするかをAPI契約として決める必要がある。
