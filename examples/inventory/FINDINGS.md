# 在庫引当で見つかった実行境界の課題

これはalpha.1での初回検証の記録です。以下の「現行API」は初回検証時点を指します。
現在の開発版での共通化結果は [REPLAY-RESULTS.md](../../REPLAY-RESULTS.md) を参照してください。

## 検証条件

- npmの `koyuki@0.1.0-alpha.1` を直接使用。本体ソースへの相対importなし。
- SQLiteに在庫、注文別引当、成功済み要求の応答を保存。
- 複数接続に同じ更新前スナップショットを明示的に取得させ、保存競合を再現。
- Node.js 26.12.0。型チェック、18テスト、デモを実行。

## 既存APIで消えた接続

3操作はすべて `defineTarget(...).on({ validate, require, evolve })` で定義できた。
各ステップの成功値の引き渡し、失敗時の短絡、取得から保存への接続を、操作ごとに展開する必要はなかった。
状態は `unreserved | reserved | confirmed | cancelled` として表し、
未検証の入力をそのまま確定関数へ渡せないことも型チェックで検証した。

## なお残る定型処理

| 残ったもの | 実装場所 | 性質 |
| --- | --- | --- |
| 成功済み応答の事前照会、競合後の再照会 | `application.ts` の `idempotent` | 複数の業務で共通化できそうな実行制御 |
| 要求を呼び出し時点で固定する処理 | 同上 | 非同期実行境界の共通責務候補 |
| トランザクション開始・commit・rollback | `repository.ts` の `transaction` | 接続の寿命・DB仕様と密接。アダプターが所有 |
| バージョン比較、在庫・引当・記録の原子的保存 | `repository.ts` の `save` | 対象集約とDBに固有。ランタイムだけでは保証不可 |
| 要求の同一性の定義、記録の保存形式 | `fingerprint` と `receipts` | ホストが仕様を決め、実行器へ渡す必要がある |

特に、再送をドメインの `require` に追加するだけでは足りない。
一度引き当てた注文はすでに入力状態が変わっているため、再送が `validate` で拒否される。
さらに、事前照会が空でも他の接続が先に保存し得る。
事前照会・原子的保存・失敗後の再照会が一つの実行契約として必要になる。
今回はその契約を共通ラッパーに記述し、業務状態に「再送済み」の枝を混ぜなかった。

## 検証結果

- 在庫不足、不正数量、注文内容の変更、終端状態からの不正遷移を拒否。
- 全在庫の引当は成功し、追加の引当は拒否。
- 別接続で同じ在庫を読んだ注文は一方だけ成功。負けた注文の再実行は新しい在庫で在庫不足になる。
- 同じ要求の同時実行は両方に同じ成功応答を返し、在庫のバージョンは一度だけ増える。
- 同じキーで異なる要求を同時実行すると一方だけ成功し、他方は `IdempotencyConflict`。
- 確定とキャンセルの競合で、両方が在庫を更新することはない。
- 実行済み記録のINSERTを故障させると、在庫と注文の更新もrollback。
- 成功後にプロセスを再起動しても、古い要求は元の応答を返す。確定済みDBは巻き戻らない。
- 事前照会とloadの間に別接続が保存するケースでも、元の成功を返す。
- 壊れた在庫集計・記録は型付きエラーとして扱う。

これはSQLite上の限定した集約の検証であり、任意のDB・分散システムでのexactly-once保証ではない。
また、入力の認証・注文の所有者確認はホストの責務で、このサンプルでは実装していない。

## 次に核へ取り込む候補

最優先は、**ドメイン検証より前に置く任意の再送・実行境界**。
今回の `idempotent` をそのまま無条件に組み込むのではなく、以下を満たすAPIを検討する。

1. 記録なし・再送・キー衝突を型で区別する。
2. 操作名と要求の同一性を結び、実行前に入力を固定する。
3. 成功済み記録の事前照会と、競合後の解決をランタイムが接続する。
4. 業務データと記録の原子的保存はアダプターの契約として残す。
5. 新規成功と再送を出力で区別し、過去の応答でViewを巻き戻さない方針を決める。
6. 業務上の失敗・不明な保存結果・更新競合を区別し、無条件の自動リトライを導入しない。

この検証では新しい公開APIを追加していない。
「業務状態・検証・遷移だけを書く」という目標に対し、処理内の接続は任せられるが、
再送と保存の周囲の実行制御にはまだアプリ側の記述が必要、という結論になった。
