予約・注文のコンポーネント合成と通常TSの比較

結論
保存→通知の一例で、業務をまたいだ再利用は実現できた。ただし同じ抽象化を通常TS関数に抽出した版にも同等の再利用性があり、JSXの優位性は実証できていない。
構想全体の否定ではない。次の設計はJSXを必須にせず、型付きの処理宣言・合成・操作の実行を核に置く方が、今回の結果には整合する。

今回作ったもの
src/comparison/kernel.ts: 型付きOperation、Program/flatMap、独自JSX factory、結果を保持するJournalとExecution。
src/comparison/domain.ts: 予約・注文の異なる状態型、純粋な入力検証、模擬保存・通知・監査アダプター。
src/comparison/components.tsx: 同じdefineCommitAndNotifyから予約用と注文用のコンポーネントを生成。
src/comparison/plain.ts: 個別TS＋Result版と、同じ手続きを共通関数に抽出したTS版。
src/comparison.test.tsx: 3実装×2業務の共通障害シナリオ、変更シナリオ、型の拒否テスト。
src/comparison/demo.ts: 3実装の結果・副作用の順序・実行履歴を出力。
scripts/compare.mjs、COMPARISON-METRICS.json: 比較fixtureの物理行数。使いやすさの指標や性能測定ではない。

再現コマンド
npm run check
npm test
npm run test:comparison
npm run demo
npm run compare

検証
型チェック成功。全90テスト成功。比較用は61件、旧版と3層版は29件。
成功する弱点テストは「問題が残ることの再現」に成功したという意味。
同じアダプターと実行基盤を3実装で共有し、JSXだけにリトライや実行履歴の利点を帰属させない比較にした。

共通シナリオ（3実装×予約・注文）
- 保存成功後に通知し、保存済みの値を返す。
- 保存競合なら通知しない。
- 通知の業務上の失敗でも、既に保存したレコードは残る。
- インフラ例外後の再試行では保存済み結果を再利用して通知を試し直す。
- 同じJournalを共有する同時実行では同じ操作を1回実行し、結果を再利用する。
- 外部成功後クラッシュは、模擬プロバイダーの同じ冪等性キーで重複排除できる。
- 冪等性のないプロバイダーではクラッシュ後に重複し、どの構文でも解消しない。

共通ルールの変更実験
「保存後、通知前に監査操作を追加する」を実装。
- 個別TS版は予約と注文の2つの関数に監査接続を追加。
- 共通TS関数版は共通のcommitAndNotifyに監査接続を追加。
- コンポーネント版は共通のdefineCommitAndNotifyに監査接続を追加。
- 各業務は監査アダプターを渡す。監査成功なら通知、失敗なら通知停止。監査失敗でも保存は取り消さない。
したがって、変更箇所が減る利益は共通化に由来し、JSX固有ではない。
今回は単一操作の監査拡張のみ。分岐や並列の大きな処理木の比較ではない。

記述量（監査拡張込みの物理行数）
- JSX共通部品の定義: 16行。
- JSXの業務ラッパー: 各3行。別途アダプターを束ねる定義が各1行。
- 個別TS手続き: 各11行。
- 共通TS関数: 12行。別途業務ラッパーが各2行。
フォーマット・型注釈の配置で変わる。行数だけで読みやすさや保守性の勝敗は決められない。
共通kernel/adapterは同じ。JSX factoryとProgramはコンポーネント版の追加概念なので、単に業務ラッパーの行数だけを比べると不公平。

型の結果
- Save/Notifyの状態の違い、予約保存→注文通知の誤接続、失敗型の欠落をコンパイルで拒否できた。
- Sはcommitから推論し、notify側にはNoInferを使い、不整合な型への拡大を防いだ。
- コンポーネントを通常の関数として呼ぶと、保存済み型と失敗UnionをProgramの型として維持できる。
- 同じコンポーネントをJSXにすると、式の型が共通のJSX.Elementに広がり、返却値と失敗Unionがunknownになる。
- JSXの各propsの制約は残るが、JSX式全体の型付き戻り値を呼び出し元に返す設計には別の型付き境界が必要。
この結果は今回の実装に対するもの。すべてのJSX APIの不可能性の証明ではない。

新たな合成上の問題
- 同じ部品を同じscopeで2つ使うとslotが衝突する。別の入力はIdentityMismatchとして拒否することを確認。
- 別scopeを付けると2つとも実行できた。部品インスタンスの安定したidentityと親子scopeの設計が必要。
- ProgramのflatMapは実行結果から次を作る関数を保持するため、v2のような全体のJSON化可能性を失う。
- 今回は実行履歴を観察できるが、全体の静的な処理木は持っていない。DevToolsの全体図や定義の永続化を現状のコードから保証できない。
- 操作nameはversionを含む信頼された識別子。同じnameで意味の異なる実装に差し替えることは検知できない。
- インフラ障害は例外、業務上の失敗はResult。業務上の失敗はこの操作IDについて完了結果として記録するので、再判定したい場合は別revision/操作IDが必要。

前回の外部IOロック問題との関係
比較用Executionは操作ごとのpendingを共有するため、遅い外部操作が別操作を止めないことを確認した。
ただしこれはインメモリの操作別調停であり、v2 FileStoreの永続化へ移植済みという意味ではない。

実験範囲
実DB・実メール・分散実行・Hono・長期の承認待ち・操作取消しは未実装。
JournalとBackendはインメモリ。新しいExecutionで同じJournalを再利用する確認であり、OSプロセス終了後の再開は保証しない。
クラッシュは例外注入。DB更新とJournal記録を一つの原子的コミットにしていない。模擬保存はIDとpayload照合によって再実行に対応。
入力はstructuredCloneで宣言・実行時に捕捉する。fingerprintはplainなJSON相当の入力に限定し、undefined/NaN等を拒否。完全な任意JS値のシリアライザーではない。

次の設計判断への提案
1. 型付きのOperation/Programを核とし、JSXは表現の選択肢にする。
2. Reactらしい合成の価値を確かめるなら、待ち合わせ・条件分岐・並列・親子scopeを含む例で、通常TSの共通関数版と比較する。
3. 処理木を静的に保持する部分と、外部結果に依存する継続部分をどう表すか決める。
4. その後に永続化adapterの契約を固める。構文だけを先に固定しない。
